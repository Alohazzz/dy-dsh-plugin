# 研发工作台文档

读取与任务对应的[文档模板](references/templates-v1.json)。已有稿件以记录的模板版本为准，按模板的必填字段和章节顺序输出。中文表达使用插件随附的 [tech-doc-style-chinese](../tech-doc-style-chinese/SKILL.md)。保留项目术语、证据、决定和理由，源码引用写仓库相对路径与实际行号。按宿主要求返回正文及结构化字段。项目、计划、议题、获批版本、实际提交、MR 和回执来自对应的宿主记录。

## 调研与执行方案

- 对照同计划其他议题，只有涉及同一业务规则及可观察结果时才补组合验收。在方案「验收与回归」内使用三级标题 `### 组合验收 · 对方议题编号`，逐项写前置条件、操作和预期。沿用已确认的同一场景。已知决定足以推导时直接写明依据，确有矛盾时在待确认问题中指出相互影响的决定。共同修改一个文件本身不构成组合验收。

- 先读议题原文、当前实现、测试和历史资料。对每项需求和验收条件记录约束、已核实证据、候选做法和可行性，使用「可实现」「满足指定前提后可实现」「当前条件下不可实现」或「证据不足」。引用旧做法时说明当时条件、本次证据及沿用或调整结论。只读调研时把需要写入或外部操作的验证列出，给出验证条件和通过标准。
- 能查证的问题先自行核实。只有影响范围、核心实现、兼容性或验收的未决事实和技术取舍才阻塞方案。需要确认时，每题只问一个决定，说明对应的需求、推荐做法和理由、可行备选及取舍。若没有可行备选，说明约束和可调整的范围。收到回答后复核选项可行性，保存答案、理由和调研版本。遇到硬性条件不可满足时说明影响，等方向确定后重新核实。
- 关键问题解决后生成可送审方案。若证据已经充分且无待定决策，可在同一轮完成报告和方案。方案逐项落到具体修改入口、实施顺序、前置条件、异常与兼容处理，以及每条需求对应的验收步骤和可观察结果。留给实施者的细节应有明确约束和判定标准。确认技术取舍与批准方案分别记录。前提改变时重评受影响的决定。

## 执行及交付

- 执行发现用户可观察行为与定稿有差异时，在「与定稿的偏差」内用三级标题 `### 可观察行为差异` 单列受影响的验收项、触发条件、定稿预期、实际表现及证据或待验证状态。将同一组场景写入测试回写。无此类差异时省略该小节。

- **执行小结**以获批版本和实际结果为依据，写清改动和偏差原因。通过和失败均保留可复查证据。尚未执行的验证记录前置条件、步骤和预期。无偏差须基于实际核对。
- **变更记录**用已确认小结提供原因和修改范围，从实际仓库与提交读取 SHA。逐议题核对归属，按模板记录小结引用。
- **云效回写**从同一执行结果生成测试正文，使用模板指定标题。只准备测试和实际价值评分及依据，实施方法留在执行小结。评分随 #5 接入，保留评分来源提供的正文和机器可读值。评分未提供时测试可以独立发布。读取旧稿时兼容旧测试标题，尚未发布的方法段跳过。以最终确认正文、远端返回或回查结果记录发布状态。远端成功但归档失败时补存记录。
- **计划完成报告**开头写原定交付、实际交付和后续事项。范围取自成员历史，逐议题结果取自小结、提交和回执。审核结论关联实际审阅版本，MR 结果和云效回写分别核对。延期、待验证和待补发事项写明去向。

## 交付前核对

保留必填章节。确无事项填「无」，缺证据填「待核实」并注明来源，待决策填「待确认」并写明问题。检查需求、决定、实施步骤和验收之间可逐项追溯。明确区分预期、实测及未验证状态。示例材料要标记模拟数据和结果。生成或修订文档本身不触发提交、发布或其他远端写入。
