# 计划议题工作流调试记录

本轮要回答一个问题：同时处理两条议题时，操作者能否留在「计划议题」列表，知道哪个 Agent 正在工作、哪条议题需要决定，以及决定前该看哪一版文档。

## 本轮起点

2026 年 11 月 20 日，已通过测试实例核实下表。时间按北京时间记录。

| 项目 | 起点 |
| --- | --- |
| 测试入口 | DSH Web 开发实例，端口 `18744`，宿主版本 `0.2.2-rc.5` |
| 插件构建 | 工作区基于 `49f0dbf`，包含未提交的任务状态改动。构建产物 SHA-256 前 12 位为 `host.js` 的 `cc152a1af22b` 和 `client.js` 的 `1cd4c6286d6e`。 |
| 计划 | HIS 工作区的「dhs测试」，计划 ID 为 `69cd686d-4c33-425e-868e-9b1fa42024ab` |
| 云效 QHDK-31298 | 未调研，未派发，过程文档 0 份 |
| 云效 QHDK-31347 | 未调研，未派发，过程文档 0 份 |

## 操作者怎样测

按平常的顺序处理两条议题，无需打开调试工具或逐步填表。遇到必须离开列表、手动刷新才看到结果、无法判断该点哪里等情况，可以在聊天中留一句「议题编号、当时看到什么、最后怎么继续」。大致时间有助于对上会话事件。测试停在某一步也可以开始复盘。

| 从列表执行的动作 | 重点观察 |
| --- | --- |
| 点击「方案调研」，等待两条议题分别出结果 | 能否看出哪条在排队、哪条在调研？其中一条需要答疑时，另一条的进度是否仍能辨认？ |
| 阅读方案，按需答疑或要求修订，再送审、定稿 | 能否找到待决定的问题、对应正文和版本？修订后能否看出哪些意见已落实？ |
| 点击「开始执行」，留在列表 | 是否仍停在原计划？排队、执行中的动效和文字是否随状态变化？收到确认请求或异常时，哪一行提示了什么，能否据此继续？ |
| 收到「小结待确认」，核对本轮小结并归档 | 在点击「确认并归档」前，从哪里读到了本轮正文？若打开了会话或文件，记录触发这一步的原因。 |
| 若本轮继续到提交或云效回写 | 能否从议题找到实际提交、回写预览及回执？记录需要切换的入口。只复盘实际走过的阶段。 |

## 执行后怎样取证

由复盘人员读取当前测试实例和工作区。先用计划 ID、工作项 ID 找到本轮绑定，再用会话 ID 和文档版本串起经过。同一议题在上轮测试中使用过其他会话，单凭议题标题会混入旧记录。

| 要核实的事实 | 本轮证据及读法 |
| --- | --- |
| 是否送达，何时真正开始工作 | 在测试实例的 `dy-yunxiao/work-*.json` 取执行绑定的 `requestId`、`sessionId`、`planVersion` 和 `dispatched`。在对应 DSH 会话按请求找消息和 `turn/start`、`turn/end`。有派发标记只证明请求已送达。 |
| 调研为何等待、修订了几轮、批准了哪一版 | 在 `dy-yunxiao/research/*.json` 按 `archive.scope.planId` 和 `issueId` 选择本轮记录。查看草稿的问题、修订意见、送审与批准记录，再核对归档方案版本。 |
| 执行何时需要人介入，如何恢复 | 列表打开时，`planExecutionStatuses` 返回绑定会话的当前状态及原因。事后用该会话的回合结束原因、授权或提问记录、后续答复和恢复执行的回合核对。只摘录解释现象所需的信息。 |
| 小结能否审定，归档是否对应本轮 | 从 HIS 工作区的 `.dsh/yunxiao/<会话目录>/task.json` 找到本轮方案和执行小结路径。核对 `execution.md` 的内容，再沿 `docs/workbench/` 当前计划的 `issue.json` 查归档文件、版本、时间及提交引用。若已发布测试评论，再核对发布回执。 |

本机测试实例的数据根目录为 `%LOCALAPPDATA%/dy-dsh-plugin-dev/`。复盘时可先在 HIS 工作区运行下面的只读命令，列出本轮已归档的文档。空结果也是线索，再查调研批次和执行绑定即可。

```powershell
$planId = '69cd686d-4c33-425e-868e-9b1fa42024ab'
$planFile = Get-ChildItem -LiteralPath 'docs/workbench' -Filter plan.json -Recurse -File |
    Where-Object { (Get-Content -LiteralPath $_.FullName -Raw -Encoding utf8 | ConvertFrom-Json).id -eq $planId }
if (@($planFile).Count -ne 1) { throw '请核对当前工作区和计划 ID' }
Get-ChildItem -LiteralPath $planFile.DirectoryName -Filter issue.json -Recurse -File |
    ForEach-Object {
        $issue = Get-Content -LiteralPath $_.FullName -Raw -Encoding utf8 | ConvertFrom-Json
        if ($issue.reference -in @('QHDK-31298', 'QHDK-31347')) {
            foreach ($doc in $issue.documents) {
                [pscustomobject]@{ Issue = $issue.reference; Time = $doc.time; Type = $doc.type; Version = $doc.version; File = $doc.file }
            }
        }
    } | Sort-Object Time
```

## 如何从记录决定改动

列表轮询返回的是当时的状态。会话和档案可以还原部分事件，但不能证明浏览器当时显示过某个动效，也不能证明操作者是否手动刷新或打开过窗口。这类差异以现场反馈或浏览器复现为依据。只有起止事件都可定位时才计算等待时长。

执行结束后，在下表按议题补入实际结果。每个问题从**首次偏离预期的一步**写起，记录用户为继续工作多做了什么。先处理阻止继续执行、提示错误对象或可能确认错版本的问题，再处理重复操作。修改后用同一动作复测，并检查另一条议题是否受到影响。

| 议题 | 实际走到哪一步 | 首次偏差与额外操作 | 证据、定位与改动 | 相同步骤复测结果 |
| --- | --- | --- | --- | --- |
| QHDK-31298 | 第二个问题答复后，调研第 3 版送审并定稿。执行会话于 20:34:22 正常结束，已生成执行小结和测试回写稿。 | 首次答疑后，列表仍显示旧问题和「修订失败」。执行阶段又遇到两个议题同时修改相同文件。 | 已修复调研回包同时含新问题和方案草稿时整轮被拒收的问题，保留已确认决定和新问题。同文件修改由 Harness 识别和处理。 | 原请求恢复后，浏览器显示新问题，本轮随后成功定稿并派发。 |
| QHDK-31347 | 初稿的 3 个问题一轮答完，调研第 2 版送审并定稿。执行会话于 20:31:22 正常结束，已生成执行小结和测试回写稿。 | 执行中发现定稿引用的 SQL 路径与当前仓库不符，并需再次确定条件入口的实施范围。 | 20:14:01 的会话提问及执行小结记录了脚本位置、条件入口及决定。 | 本轮已按确认结果实施。方案定稿前核验依据、列表内答复均为后续改进建议。 |

## 执行阶段复盘

本轮评估到两份执行小结及测试回写稿生成。归档未测试，留待单独讨论。本地构建失败、构建重试和环境排查耗时均排除。下列时间用于核对事件顺序，不能据此把整个暂停区间计为可节省工时。

| 优先级 | 本轮证据 | 建议及复测条件 |
| --- | --- | --- |
| 1．从议题行处理执行提问和暂停 | QHDK-31298 的第一回合于 20:09:58 以「已按你的选择暂停本议题执行」结束，20:28:11 操作者追问剩余工作。当前宿主对原生提问只返回「等待用户答复」或「等待操作授权」，尚无独立的暂停状态。按代码推断，已暂停、回合正常结束且尚无小结时，可被归为缺少小结的执行异常。当时页面实际文案待核实。 | 在该行展示问题、阻塞原因和下一步。业务问题可原地答复，选择暂停后显示「已暂停」及剩余事项，恢复动作沿用原会话；需要宿主授权时保留对应入口。复测时确认暂停后不报失败、恢复后不重复派发，另一行继续更新。 |
| 2．定稿前核实依据，集中确认范围 | QHDK-31298 分两轮分别确认「有保存值」和「显式清空」的语义。QHDK-31347 的初稿一次列齐了 3 个问题；执行时又查到方案引用的 SQL 文件仅有 99 行，所引第 1138 行不在该文件。 | 同一规则的已知边界尽量在首次答疑列齐。Agent 在送审前核对路径、符号和近期仓库惯例；条件入口写明触发条件及无法核实时的处理方式。复测时核对送审依据可定位，仓库已能回答的技术问题无需操作者再次选择。 |

本轮两个会话都编辑了相同文件，QHDK-31298 的执行小结记录了注释被覆盖后重新应用。操作者确认 Harness 能识别并处理同文件修改，据此撤回插件按文件排队的建议。

## 从交付文档看还有哪些改进

| 建议顺序 | 本轮依据 | 下次如何判断改进有效 |
| --- | --- | --- |
| 1．在计划列表审阅本轮变更 | QHDK-31298 经过 3 轮调研。预览提供本轮意见、当前全文和可展开的旧稿。两条议题的列表版本分别为 v3、v2，对应的执行方案文件都是 v1。 | 从议题行打开审阅时，显示「第 3 轮调研 · 执行方案 v1」。列出上一轮答复改动了哪条规则、还需确认什么，并可定位原文。首次生成执行方案时明确标出首稿，后续修订与上一版同类文档对照。 |
| 2．让执行中发现的行为变化进入测试交接 | QHDK-31347 的定稿要求参数关闭时保持原行为。执行小结第 7 项记载，档案中有关系值时，下拉框现在可能显示该值。小结把这项差异关联到 A1，测试回写稿的 A1 仅覆盖首诊面板为空。 | 从议题行查看执行结果时能看到受影响的定稿条目、输入条件和预期差异。测试回写稿保留首诊场景，并单列「参数关闭、档案已有关系值」待验证。是否需要操作者确认取决于该变化是否超出定稿。 |
| 3．为同一业务规则补组合验收 | QHDK-31298 规定当前处方保存值优先、清空后走兜底。QHDK-31347 又允许在参数开启时用患者本人补空。两份定稿各自描述了代办人的取值。 | 两条议题引用同一组组合场景。至少核对「已保存其他代办人，再开启本人兜底」和「清空后无历史、无联系人且启用本人兜底」。已有决定能确定预期时直接沿用，只将仍有歧义的场景交给操作者。 |

## 下一轮复测起点

测试实例已加载上述三项改动。通过端口 `18744` 的工作台接口核对，「dhs测试」仍含 QHDK-31298 和 QHDK-31347，两条议题均无调研记录、执行绑定或过程文档。本轮代码改动和专用验证程序已清理。

- **送审时**，从议题行核对调研轮次、执行方案版本、本轮落实的决定和待确认问题。首次形成方案时标记首稿，修订同类文档后可展开变更章节，对照两版原文。
- **有组合验收时**，从任一相关议题查看同一场景和来源。执行任务清单记录派发时计划内已定稿的相关场景及其版本。下一轮重点观察两个 Agent 能否依据议题材料识别同一业务规则，并写出可执行的预期。
- **执行结束后**，在议题行打开「审阅执行结果」。若小结记录可观察行为差异，应能看到触发条件、定稿预期、实际表现或待验证状态，并在测试回写稿中核对同一场景。旧小结保留全文供核对。
