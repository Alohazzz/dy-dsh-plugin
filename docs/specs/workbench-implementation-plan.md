## 建议的文档归档结构

当前调研批次保存在 DSH 用户目录的 `dy-yunxiao/research` 下，执行材料位于执行检出的 `.dsh/yunxiao/<会话摘要>/`，包含 `issue.md`、`plan.md`、`task.json` 和由 Agent 写入的 `discussion.md`。建议保留这些运行路径和回写解析约定，把可复用的文档放到**创建计划时选定的稳定项目工作区**。独立检出删除后，项目档案仍可查阅。

建议默认目录如下。每个议题目录表示它参与某次计划的记录，通过组织、云效项目、工作项 ID 和计划 ID 确定身份；展示编号和标题用于检索。目录名使用经校验的路径安全标识。

```text
<项目工作区>/docs/workbench/
  README.md                           # Agent 查档入口、归档约定与检索步骤
  manifest.json                       # 归档格式与脚手架版本
  <组织键>/<项目键>/
    index.json                        # 可从计划和议题清单重建
    plans/<计划ID>/
      plan.json                       # 目标、成员变动、阶段、MR、遗留事项
      completion.draft.md             # 提交合并时生成，返工时更新
      completion.md                   # 关闭时保存的终稿
      issues/<工作项ID>/
        issue.json                    # 编号、模块、阶段、文档版本与替代关系
        research-v1.md                # 调研证据、历史复用结论和待确认项
        proposal-v1.md                # 送审快照；修订递增版本
        reviews.json                  # 审核人、意见、结论和对应版本
        execution-v1.md               # 执行小结，标明依据的获批版本
        changes.json                  # 每次实际提交的仓库、SHA、原因及范围
        publication.json              # 开发向／测试向发布正文、评分依据与回执
```

每份正式文档记录适用版本或日期、来源和关联证据。批准时在清单中指向确切方案版本。返工时追加版本，原审批记录仍指向原文。计划终稿从成员变动记录取原始范围和调整原因，从执行小结、提交及远端回执取实际结果。未验证项保留原状态。提交后的档案可记录业务提交 SHA，避免文档在同一次 Git 提交中引用自身 SHA。

索引至少覆盖项目、业务模块、议题编号、计划、业务关键词和被替代的记录。调研 Agent 先查索引，跨议题问题先读计划终稿，再按需读取报告、获批方案、小结和提交。核对当前代码或测试后，在新报告中逐项写明来源、适用条件、当前证据及「沿用／调整／待确认」。索引损坏时可从清单重建，缺少历史资料时继续调研并注明缺口。

## 安装、初始化和升级

| 时机 | 建议的宿主行为 | 可验证结果 |
| --- | --- | --- |
| 构建安装包 | 在插件内增加版本化模板资源，提供调研报告、执行方案、执行小结、变更记录、回写、计划完成报告及清单初值；纳入 npm 的 `files` 白名单。生成入口复用已有中文写作技能，保留交付稿的两个回写章节。 | 用 `npm pack` 生成实际安装包，从包内加载每种资源，检查模板、占位字段和写作规则均可用。 |
| 安装并加载插件 | 宿主从已安装包定位并校验模板清单，沿用现有技能注册入口。项目选择发生在安装之后，安装到 DSH 时只准备插件资源。 | 在无工作区的干净 profile 安装并重启，可识别模板版本；缺少资源时给出具体文件和修复提示。 |
| 首次选择目标项目并创建计划 | 宿主按实际工作区解析归档根，初始化入口说明、版本清单和项目索引，创建计划清单。已有计划在首次需要归档时执行同一初始化。 | 重复初始化、两个计划同时创建或中途失败后重试，均保留已有档案；同名自有文件发生冲突时报告具体路径，保留原文件。 |
| 阶段产物就绪 | 宿主在收到调研结果、送审、定稿、执行小结、提交、回写回执或关计划时，从包内模板生成对应材料。只读调研 Agent 只返回内容，由宿主验证后落盘。执行 Agent 沿用任务清单指定的路径。 | 初始化后不会出现一套看似已完成的空报告。保存正文后更新清单和索引；以计划、议题、事件及版本去重，同一回执重放只产生一条记录。 |
| 升级、恢复和卸载 | 新模板用于后续生成。宿主按格式版本补齐缺失字段，遇到较新且无法识别的格式时提示升级。历史计划优先从现有定稿、任务清单、交付稿和回执建立引用；缺失来源标记待核实。卸载保留项目档案。 | 使用含人工修改的旧档案进行升级、重复升级及卸载验证。正文、旧回写预览和历史引用均可继续读取。 |

档案可能随项目共享。归档只写业务正文、相对文件引用和必要的远端标识，凭据、临时附件地址和个人会话运行状态沿用宿主存储。对于写入失败，保留原始材料和待归档状态；远端操作已成功时只重试本地归档，避免再次发表评论或发起合并。

### 工作流文档的生成与校验

| 责任方 | 交付与边界 |
| --- | --- |
| 研发工作台文档编写 Skill | 按调研、送审、执行、提交和计划汇总等任务选择模板，说明各节从哪里取材、如何引用证据，以及缺少证据时如何标记。中文措辞与排版复用 `tech-doc-style-chinese`。调研、执行和汇总入口引用同一套规则。 |
| 版本化模板 | 作为格式的唯一来源，定义文档类型、格式版本、必填字段、章节名称和顺序。覆盖调研报告、执行方案、执行小结、变更记录、云效回写、计划完成报告，并随包提供入口说明和清单初值。Skill 按类型和版本引用模板。 |
| 插件宿主 | 从安装包加载 Skill 和模板，绑定项目、计划、议题及模板版本，按该版本校验字段、章节、顺序和必填正文。获批版本、提交 SHA、MR 结果和回执取自对应记录。校验通过后保存带版本的快照；失败时指出文件、具体缺项和补正方法，保留原稿供重试。 |

执行小结依次记录「执行依据」「实际修改」「与定稿的偏差」「验收结果」「待验证项」。已运行的步骤记录实际结果和证据，未运行的场景列入「待验证项」。同一份执行结果生成归档小结与 `discussion.md`。其中修改范围与偏差生成 `## 修改方案汇总`，测试条件、步骤、预期、实际结果与待验证项生成 `## 影响范围与测试`。两段各出现一次且正文非空，沿用现有开发向、测试向预览与确认发布流程。

**验收条件**

- [ ] 用 `npm pack` 生成实际安装包，在无工作区的干净 profile 安装并重启。能加载专用 Skill、全部模板及版本清单；缺少资源时提示具体文件和修复方法。
- [ ] 从首次生成和修订入口生成同类文档，必填字段、章节和顺序与同版模板一致。给定已执行失败和未执行的测试各一项，小结分别保留失败证据和待验证步骤。
- [ ] 分别输入缺少必填字段、必填节为空、重复章节及章节错序的材料。宿主定位问题，补正后才保存正式快照；快照中的归属、获批版本和已有远端结果可与源记录核对。
- [ ] 用同一份执行结果生成小结和交付稿，通过现有解析器分别预览开发向与测试向正文。核对修改范围、偏差和测试结果一致，现有预览编辑、确认发布和部分失败补发仍可用。
- [ ] 用旧交付稿验证标准标题及既有的「影响范围与测试（测试向）」标题均可解析。升级模板后，旧档案按记录的原版本读取，原正文和历史预览可继续使用；新生成的档案记录新版本。

### 切换项目时如何建档

模板随插件安装一次。每次切换项目，宿主根据「当前选定的稳定工作区＋云效组织 ID＋云效项目 ID」重新定位档案，清除上一项目的活动计划和检索范围。项目名称用于显示，项目改名后仍按原 ID 查档。

| 场景 | 切换后的行为 |
| --- | --- |
| 同一工作区，从云效项目 A 切到 B | 复用工作区的入口说明和格式清单。B 已有项目索引时直接加载；首次浏览 B 时显示尚未建档，首次创建计划或给已有计划归档时初始化 B 的项目目录和索引。A 的档案保留在 A 的目录。 |
| 切到另一个本地工作区 | 从新工作区定位归档根。若项目仓库已带有档案，直接读取；若归档根缺失，在首次写入时使用已安装的模板初始化。跨机器或跨工作区共享历史时，需要让档案随项目仓库同步，或将已有档案迁入目标工作区。 |
| 返回已有项目，或打开计划的独立检出 | 返回项目时加载对应项目索引。通过计划打开独立检出时，使用计划记录的稳定工作区定位同一份档案。索引缺失但已有清单时，先重建索引，保留已有正文。 |

切换只触发读取。首次写入时由宿主自动补齐目录，无需用户执行命令。后台调研、执行和回写任务沿用启动时绑定的工作区、项目和计划；即使用户已切换到 B，A 的任务仍归档到 A。验收时应覆盖「在 A 启动调研 → 切到 B 创建计划 → A 的调研完成 → 返回 A 查阅报告」，并核对两个项目的索引和文档归属。

## 按依赖顺序实施

| 顺序 | 前置 | 交付内容 | 验收条件 |
| --- | --- | --- | --- |
| 1. 确定状态与档案契约 | 需求文档 | 定义议题五阶段、计划四阶段、各阶段触发动作和依据。约定归档根、标识、版本及成员历史。区分本地进度、云效状态、MR 状态。明确一个旧议题再次入计划时如何关联既有会话和本次执行。 | 用旧计划、两议题独立推进、退回修订、移出后再次入计划四个样例验证状态表与档案归属。 |
| 2. 交付文档编写 Skill、模板与工作区脚手架 | 1 | 按 [#26](https://github.com/Alohazzz/dy-dsh-plugin/issues/26) 交付专用 Skill、模板和宿主校验，再按 [#27](https://github.com/Alohazzz/dy-dsh-plugin/issues/27) 接入工作区初始化、归档读写与索引重建。 | 通过上列文档生成与校验场景，再验证跨检出访问、并发初始化和失败恢复。 |
| 3. 打通单议题调研与定稿 | 2 | 在调研技能中加入查档步骤，拆分调研报告和方案，复用答疑与修订。宿主保存送审、退回、批准记录，执行会话读取获批版本。 | 用一条历史规则和一个替代决定发起新调研；报告给出引用及核实结论。方案退回后保留前版，执行只读取当前获批版。 |
| 4. 打通执行、提交与回写 | 3 | 从交付稿归档执行小结，补确认与重新送审。关联实际提交，按议题生成变更记录。扩展现有回写预览，保留价值评分依据、测试步骤及最终发布内容。 | 两议题同属一计划时可分别追溯 SHA。第二条评论失败后只补发该条。实际验收结果与建议测试场景可分别查阅。 |
| 5. 完成计划汇总、审核与关闭 | 2、4 | 在计划创建和成员调整时保存范围历史；发起或关联 MR 时生成报告草稿。返工后更新议题资料和草稿，核实 MR、回写及剩余事项后归档终稿。 | 用含已交付与延期议题的计划走完整流程。MR 已合并时仍能识别待补回写项；终稿列出原定范围、实际结果及遗留去向。 |
| 6. 验证升级与跨计划复用 | 3、4、5 | 从旧安装升级，验证旧记录读取与按证据补录；在另一计划中用模块名和业务关键词查到上一计划终稿及议题证据。 | 在隔离 Desktop profile 用实际安装包验收，覆盖重启恢复、索引重建、替代关系、远端待核实和无历史命中场景。 |

建议先用一个项目、一个计划、一个议题验收第 1 至 3 步，确认安装包中的模板能在真实工作区生成可追溯的获批方案，再扩展到执行与计划汇总。计划范围历史应从第 2 步首次创建新计划时开始记录，以便第 5 步生成报告时有原始依据。
