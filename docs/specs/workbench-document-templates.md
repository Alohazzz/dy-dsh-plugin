# 研发工作台文档模板与编写要求

供 GitHub #26 实施前确认。六类模板各自声明文档类型、模板版本、必填字段和有序章节。模板中的标题是宿主校验依据，首次生成和同版修订共用同一定义。[生命周期与档案契约](workbench-lifecycle.md)

## 模板章节与取材

| 文档 | 固定章节或字段 | 取材要求 |
| --- | --- | --- |
| 调研报告 | 业务背景与范围 → 业务规则与例外 → 现状与证据 → 历史结论核对 → 影响范围 → 需求逐项可行性 → 待确认问题与结论 | 从云效原文、当前实现与历史档案取材。逐项评估目标、约束和验收条件是否能达到，记录候选做法、依据及缺口。历史结论写明来源、适用条件、本次证据和沿用、调整或待确认。 |
| 执行方案 | 目标与范围 → 实施依据与已确认决策 → 修改范围与实施步骤 → 验收与回归 → 风险与异常处理 | 引用调研报告版本和已确认决策。依据已验证的条件写出选定做法、修改入口、步骤和可观察的验收结果。修订时保留仍适用的决定与理由。 |
| 执行小结 | 执行依据 → 实际修改 → 与定稿的偏差 → 验收结果 → 待验证项 | 引用获批版本。列出实际修改与偏差原因。已运行的测试写实际结果及证据，失败写失败表现及原因。未运行的测试列入待验证项。 |
| 变更记录 | 仓库标识、提交 SHA、议题归属、变更原因、修改范围、执行小结引用 | 宿主从实际提交读取仓库与 SHA。原因和范围来自已确认的执行小结，并核对该提交实际覆盖的议题。 |
| 云效回写 | 测试、价值评分及依据、发布回执 | 归档用户最后确认的正文，回执来自远端发布与回查。本批先交付测试回写，价值评分随 #5 接入。 |
| 计划完成报告 | 交付概况 → 原定范围与变动 → 逐议题交付与验证 → 合并与审核结果 → 遗留事项 | 概况写原定目标、实际交付和后续事项。正文引用成员历史、小结、提交、MR 和回执。草稿与终稿使用同一章节定义，各自关联对应证据。 |

## 从调研到可送审方案

1. **先核对可行性。** 每个目标和验收条件记录对应的业务约束、可复用的入口或能力、候选做法、已核实证据和可行性结论。结论使用「可实现」「满足指定前提后可实现」「当前条件下不可实现」或「证据不足」。根据议题检查影响方案的接口、数据、权限、依赖、兼容性及验证条件，写明依据对应的代码版本或环境。只读会话先查代码、现有测试、契约和已授权的只读资料。需要实际写入或外部操作才能证实的前提，记录最小验证方式、所需条件和通过标准，取得证据后更新报告。
2. **集中确认会改变方案的问题。** 能靠证据解决的技术细节由 Agent 先核实。需要业务或技术取舍时，每题关联一个受影响的需求或验收条件，给出推荐选项、依据、可行备选与取舍，并说明答案会改变哪些模块、行为或验收结果。采用其他答案时，先复核其可行性。影响改动边界、核心实现路径、数据兼容或验收的证据缺口及技术决定，解决后才生成可送审方案。保留已确认答案、理由和对应的报告版本。
3. **确认后生成可落地的方案。** 以最新调研结论和已确认答案为输入。逐步写明修改模块或入口、所依赖的前提、正常和异常路径、数据兼容策略，以及验证步骤和预期结果。按需求逐项核对是否有对应实施步骤和验收证据来源。执行 Agent 应能依据方案直接开展工作。影响面可控的实现细节可以留到执行时决定，写明约束和判定标准。

已核实所有关键条件且无待定决策时，可直接生成方案。发现硬性条件不可满足时，报告说明影响及可行的范围调整或替代做法，等用户确定方向后重新核实。执行前若证据或前提发生变化，重新评估受影响的决定，必要时修订并送审。

### 验收样例

| 输入 | 应观察到的结果 |
| --- | --- |
| 新计划需要复用历史证据，旧执行会话按工作区和工作项查找。 | 报告引用现有绑定代码，说明直接复用会把不同计划的执行记录混在一起。推荐复用历史证据并新建执行绑定，说明其对旧绑定兼容和跨计划验收的影响。 |
| 用户确认采用新绑定，并要求保留旧交付稿读取。 | 方案写明新绑定的归属、旧绑定查找顺序和归属检查，以及同次重试、移出后重入、跨计划读取旧稿的验收步骤。确认结果能追溯到报告和答疑记录。 |
| 实际权限缺失，无法核实影响实现路径的远端能力。 | 调研报告保留证据缺口和验证条件。前提核实或替代做法确认前，议题保持调研阶段。 |
| 各项条件已有充分证据，技术做法沿用现有契约。 | 直接生成方案，引用对应证据和现有契约。 |

## 通用编写要求

- 用仓库的 `tech-doc-style-chinese` 审校。正文保留业务规则、决定及理由、适用条件、例外、失败处理与验收标准。合并重复章节或段落中的同义表述，保留同版模板的必填标题。
- 引用关联议题、文档版本、仓库相对路径和行号或远端记录。历史材料注明适用条件。跨计划结论同时给出本次核实证据。
- 必填章节始终保留。证据已核实且确无事项时写「无」。待外部证据时写「待核实」并注明需要核实的来源。待业务或技术决定时写「待确认」并说明问题。验证结果按通过、失败和待验证分别记录。待验证项给出前置条件、步骤和预期。
- 宿主写入文档类型、模板版本、项目、计划、议题和相关版本引用。获批版本、实际提交 SHA、MR 结果、回执以源记录为准。校验缺字段、标题重复、章节错序或正文为空时，提示具体文件和补正方法，保留原稿。
- 使用包内同版模板生成与校验。正式快照记录模板版本，旧快照按原版本读取。入口说明和清单初值随包交付。

## 云效回写格式

归档小结和 `discussion.md` 共用一份执行结果。修改范围、实现方法和方案偏差留在执行小结，供项目内查阅。云效新增发布内容限于下表两项。

| 回写内容 | 编写和发布要求 |
| --- | --- |
| 测试 | `discussion.md` 中使用 `## 影响范围与测试`。写明测试范围、前置条件、用例步骤、预期、实际验证结果和待验证项。 |
| 价值评分 | 保存实际评分与依据。随 #5 接入，本批测试回写可独立预览、确认、发布和补发。 |

读取旧稿时继续接受 `## 影响范围与测试（测试向）`，忽略 `## 修改方案汇总` 中尚未发布的内容。已有发布正文和回执可作为历史记录查阅。云效发布沿用预览、编辑、确认和失败补发流程，归档正文以最终确认版本为准。
