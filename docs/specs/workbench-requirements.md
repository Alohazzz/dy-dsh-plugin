# 研发工作台需求文档

本文描述研发工作台的目标流程。开发人员从云效议题出发，为一次交付创建计划。Agent 按议题调研和执行，审核人先审核单个议题的执行方案，再审核计划所包含的实际变更。交付后，其他 Agent 可以追溯当时的决定，并核实这些决定对新需求是否仍然适用。

本文中的「议题阶段」指议题在本次交付计划内的进度。云效工作项状态、评论回写结果和 Codeup 合并结果分别以对应平台的记录为准。已有的单议题直接开工入口、云效操作确认和合并请求关联规则见[云效议题插件第一版规格](yunxiao-v1.md)。

## 议题生命周期

一个计划可以包含多个议题。每个议题独立经历「调研 → 待审核 → 定稿 → 执行 → 提交」。同一计划内，一个议题等待审核时，其他议题可以继续推进。

| 阶段 | 工作与产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 调研 | Agent 阅读云效原文、历史档案和当前实现，形成《调研报告》，记录业务场景、规则与例外、现状证据、影响范围和待确认问题。依据报告编写《执行方案》草稿，列出拟修改范围、实施步骤和验收标准。 | 报告和方案草稿已关联议题，可一并送审。 |
| 待审核 | 审核人对照需求和证据审阅方案，记录审核意见及处理结果。需补充事实时退回调研，需调整步骤时修订草稿并复审。 | 审核人认可指定版本的方案。 |
| 定稿 | 保留审核通过的《执行方案》，记录最终决定、选择理由、适用条件，以及影响决策的备选方案和取舍。 | Agent 能定位获批版本并据此开始执行。 |
| 执行 | Agent 按定稿方案实施，形成《执行小结》，列明实际修改范围、方案偏差及原因、验收步骤、实际结果和遗留限制。尚待测试的场景单列。 | 实际修改和验收结果经确认，可以提交。若需改变已批准的范围或验收标准，修订方案并重新送审。 |
| 提交 | 提交代码时形成《变更记录》，说明为什么改、改了哪里，关联议题与实际提交。根据小结准备云效开发向和测试向回写内容，包含价值评分及依据、测试方向、前置条件、用例步骤和预期结果。 | 工作台可从议题追溯到提交。回写另行预览、确认并记录逐项回执，提交成功与回写成功分别展示。 |

## 计划生命周期

| 阶段 | 工作与产物 | 阶段结果 |
| --- | --- | --- |
| 创建 | 开发人员从议题池选择一个或多个议题生成交付计划，也可以将议题加入已有计划。记录计划目标、初始议题清单、工作区、交付分支和计划完成日期。 | 各议题分别推进。后续延期、移出或追加议题时，保留范围变化及原因。 |
| 提交合并 | 核对本次拟交付议题和实际提交，发起或关联 Codeup 合并请求。根据议题产物生成《计划完成报告》草稿。 | 审核人可从草稿查看本次提交合并的范围、验证情况，以及延期或移出的议题。 |
| 审核 | 审核人结合报告草稿、代码变更和验收结果审核整批交付，记录意见。需要返工时，更新受影响议题的方案或小结、相应提交和报告草稿，再次送审。 | 保留审核结论与对应的合并请求。工作台回查实际合并结果。 |
| 关闭 | 核对合并结果、议题交付情况、云效回写回执和遗留事项，形成《计划完成报告》终稿。 | 归档终稿。延期、待验证或待补回写的事项列明当前状态和后续去向。 |

### 计划完成报告

报告首段回答三个问题：计划原本要交付什么，实际交付了什么，还有什么需要跟进。跨议题依赖、整批变更的影响和实际合并结果在计划层说明。

正文按议题列出原定目标、交付情况、实际变更及原因、验收结果、云效回写状态和原始记录链接。原定目标取自定稿方案，实际交付依据执行小结和变更记录，合并与回写依据对应平台的结果。尚无结果时标记「待核实」。审核返工后更新同一份报告，关闭时保留最终版本。

## 归档范围与用途

| 材料 | 归档要求 | 后续调研用途 |
| --- | --- | --- |
| 调研报告 | 按议题归档，保留证据来源、适用条件和未决问题。 | 查业务背景、历史规则及例外，确定需要重新调查的部分。 |
| 定稿执行方案 | 按议题归档，保留获批版本及审核结论。方案被修订时保留版本关系。 | 查当时的决定、理由，以及哪些条件变化后需要重新评估。 |
| 执行小结 | 按议题归档，保留实际结果、偏差和未验证项。 | 查实际完成范围和已验证场景，识别方案与交付的差异。 |
| 计划完成报告 | 按计划归档终稿，链接成员议题、议题档案和合并请求。 | 作为跨议题调查入口，查一次交付的全貌、依赖及遗留事项。 |
| 变更记录 | 随提交保留，议题档案保存提交引用及改动原因。 | 核实某条规则在哪次提交中改变，并定位受影响的代码。 |
| 云效回写内容 | 按议题保留已发布内容和回执。测试用例保留步骤与预期结果，价值评分保留依据。 | 测试用例可作为回归候选，历史评分可供类似需求估值时参考。 |

方案草稿、报告草稿和审核往返意见作为过程记录，关联到相应的定稿或终稿。归档记录应能按项目、业务模块、议题和计划查找，并标明适用版本或日期。后续议题替代旧结论时，从旧记录链接到新决定，保留原结论当时成立的条件。

## Agent 调研新需求时的查阅与复用

1. **从新议题提取检索线索。** 识别所属项目、业务模块、涉及的业务动作、规则或异常场景。已知关联议题时按编号直查，涉及多个模块或一次历史交付时，先查计划完成报告，再进入相关议题。
2. **按问题选择材料。** 查背景和例外先读调研报告，查决定和取舍再读定稿方案。判断已有能力时读执行小结，必要时沿变更记录查实际提交和合并结果。从云效测试用例中挑选与新需求条件相符的场景。
3. **核实当前适用性。** 检查历史材料的版本、适用条件及后续替代记录，对照当前需求、目标分支实现或可复核的测试结果。遇到冲突、证据缺失或历史未决项时，记录差异并补充调查。
4. **在新调研报告中说明复用结果。** 对每项影响方案的历史结论给出来源、当时条件、本次核实依据，以及「沿用」「调整」或「待确认」的判断。引用历史用例时保留原预期，本次执行后再填写实际结果。

例如，新议题要求调整「退回后重新审核」的规则。Agent 可先查原议题的调研报告，找出哪些角色和退回原因受该规则约束，再读定稿方案和执行小结，核实最终实现的范围。若后续计划只修改了其中一种退回原因，就在新报告中分别记录仍适用的规则和已被替代的规则，并引用相应议题与用例。

## 验收场景

- **多议题独立推进。** 同一计划内，一个议题退回调研，另一个按已定稿方案执行。两者的阶段、文档版本和审核意见均可单独查阅。
- **提交与回写可核对。** 从已提交议题能定位变更原因、代码提交及执行小结。测试向评论发布失败时，可看到开发向评论的成功回执和待补发项。
- **计划范围可对账。** 一个计划同时含已交付和延期议题时，报告草稿分别列出两者。关闭后，终稿能追溯实际合并结果、验收记录和延期原因。
- **历史结论可复核。** 从新议题的业务场景能找到旧报告和替代它的后续决定。新调研报告注明采用的结论、来源与当前依据，并列出仍需验证的场景。
